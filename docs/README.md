# Flint Documentation

This directory is the maintained documentation set for Flint. It separates current contracts and operational guidance from the accepted target architecture that is still being migrated.

## Status note

The application currently ships as a **partially modularized monolith**:

- Rust now uses a Cargo workspace rooted at `src-tauri`. The host package remains `flint`; the three foundation crates, seven extracted feature crates, two mod provider crates, and six loader provider crates are extracted. `flint-core` owns shared path/network/error policy and object-safe typed port contracts. All seven feature crates are extracted; the Phase 4 checker gate is implemented, while Phase 5 remains pending.
- All nineteen Cargo workspace packages share the generated date-based release version: the host `[package] version` matches `[workspace.package] version`, and non-root members use `version.workspace = true`. Release tooling keeps the host and workspace versions identical and updates every local `Cargo.lock` package entry as part of the same five release paths (`VERSION`, `package.json`, `src-tauri/tauri.conf.json`, `src-tauri/Cargo.toml`, `src-tauri/Cargo.lock`).
- The typed ModProvider and LoaderProvider **API and provider-crate milestones** are implemented in `src-tauri/crates/flint-provider-api`, two mod provider crates, and six loader provider crates under `src-tauri/providers`. The host builds one immutable mod registry and one immutable loader registry in `provider_composition.rs`, injects them into provider-backed commands, and keeps one `ModSource` binding in `mods.rs` plus one `LoaderKind` binding in `loaders.rs`. Source-specific HTTP/payload mapping lives in the extracted provider crates and uses `flint-core` ports. Full provider runtime lifecycle hardening and Phase 5 remain pending; the Phase 4 checker gate is active.
- Phase 2 LoaderProvider is **milestone implemented: six loader leaves and typed host adoption; full runtime phase pending.** `src-tauri/modules/flint-feature-loaders/src/lib.rs` owns the sole `LoaderKind` binding and typed orchestrator while the host `src-tauri/src/loaders.rs` adapter adapts progress sinks/events over the immutable registry built in `provider_composition.rs`. It builds typed list/install contexts from `ReqwestNetwork`, `SafeWorkspace`, `ProcessJavaRunner`, feature progress sink boundaries, logger/deadline/cancellation, preserves the 75-second metadata / 600-second installer HTTP / 600-second Java timeout split, and retains command/event/DTO behavior. Provider runtime lifecycle hardening and Phase 5 remain pending; the Phase 4 checker gate is active.
- Phase 3 contribution registry is implemented in `src/core/contributions.ts`, `src/app/composition.ts`, `src/app/App.tsx`, `src/app/AppSidebar.tsx`, `src/modules/settings/index.tsx`, and `src/modules/launch/index.tsx`. Pages, navigation, five settings sections, and a launch-navigation instance action are populated and mounted. `AppPageContext` exposes the frozen slot lists; `src/core/ContributionBoundary.tsx` and `src/core/InstanceActionRenderer.tsx` provide the shared renderers.
- `scripts/check-architecture.mjs`, its tests, and the release workflow architecture gate implement the Phase 4 gate. The `flint-release.yml` `prepare` job runs the checker tests, then `node scripts/check-architecture.mjs --phase 4`. The active gate enforces frontend boundaries, the exact nineteen-package Cargo workspace, internal/external dependency allowlists and cycles, one root lockfile, all nineteen production source roots, forbidden provider raw I/O/Tauri/process/feature/host patterns, typed `LoaderProvider`/`ModProvider` context ports, both immutable composition registries, exact six loader descriptors/requirements, the sole `LoaderKind` binding, exact allowlists, and the 30-command/28-feature-command gate map. Legacy loader adapter/API alternatives and waivers are rejected fail-closed. Phase 5 checks remain inactive.
- Phase 4: the nineteen-crate workspace, shared core policy/typed-port contracts, typed mod/provider APIs with two mod and six loader implementation crates, two host composition registries, the host lifecycle/availability milestone, and the Phase 4 checker gate are implemented. `flint-feature-api` provides the feature descriptor, validated registry, lifecycle coordinator/state machine, and availability DTO; `src-tauri/src/feature_host.rs` composes seven explicit features and real provider metadata, starts in Tauri setup, publishes the ungated `get_host_availability` snapshot, gates all 28 feature commands, filters frontend contributions, and shuts down on exit. All seven feature crates are extracted; full provider runtime lifecycle hardening and Phase 5 remain pending.
- Existing command names, arguments, success results, DTOs, and events are preserved. Phase 4 adds the ungated `get_host_availability` command and gating/error behavior for the 28 existing feature commands, documented in `API_CONTRACT.md`.

Typed loader/mod provider adoption and the six loader leaves are implemented at milestone level. All seven feature crates are extracted; the Phase 4 Cargo-metadata/source/typed-port gate is active, while full provider runtime lifecycle hardening and Phase 5 remain planned. The nineteen-crate workspace, typed loader/mod provider APIs, generic core Minecraft support, eight provider implementation crates, feature lifecycle API, host lifecycle/availability IPC/gating, and snapshot-driven frontend filtering are implemented.

Canonical ownership: [`ARCHITECTURE.md`](ARCHITECTURE.md) is the detailed source for boundaries, provider/registry semantics, lifecycle, frontend contributions, and phases; [`DEVELOPMENT_STANDARDS.md`](DEVELOPMENT_STANDARDS.md) owns process/checklists/concise summaries; the [Architecture Decision Record](architecture-decision-records/0001-modular-core-and-feature-modules.md) documents rationale/consequences; this README is the index/source-of-truth map.

## Reading order

1. [`ARCHITECTURE.md`](ARCHITECTURE.md): read the canonical phase-status table first, then the current baseline, target rules, provider/lifecycle/event semantics, Phase 4 checker scope, and remaining migration sequence.
2. [`DEVELOPMENT_STANDARDS.md`](DEVELOPMENT_STANDARDS.md): start with the partial-Phase 1/2, implemented-Phase 3, and Phase 4 checker-gate cross-reference and transition path, then use the phase matrix and apply the implementation, security, checklist, review, and delivery rules.
3. [`architecture-decision-records/0001-modular-core-and-feature-modules.md`](architecture-decision-records/0001-modular-core-and-feature-modules.md): understand why the architecture was accepted and which alternatives were rejected.
4. Read [`API_CONTRACT.md`](API_CONTRACT.md) and [`FEATURE_API_CONTRACT.md`](FEATURE_API_CONTRACT.md) for the area being changed.
5. Read [`INTEGRATIONS.md`](INTEGRATIONS.md) for setup, local storage, privacy, and selected-instance behavior.
6. Use [`CODE_REVIEW.md`](CODE_REVIEW.md) only as a historical readiness snapshot, not as current CI evidence.

## Documentation rules

- Label behavior as **Implemented**, **Partially implemented**, **Planned**, or **Deferred**, and identify the migration phase/milestone. Never present full provider runtime lifecycle hardening or Phase 5 checks as implemented/active before they are. The typed mod/loader APIs, eight provider implementation crates, extracted settings/saves/accounts/vanilla/launch/mods/loaders feature crates, typed host loader adoption, two immutable composition registries, host lifecycle/availability IPC/gating/filtering milestone, and the Phase 4 Cargo-metadata/source/typed-port checker gate are implemented and may be stated as such; full provider runtime lifecycle hardening and Phase 5 remain pending.
- Use only relative Markdown links that resolve inside `docs/`. Do not link to another checkout, an external site, or a repository file outside the documentation tree.
- Update the affected authoritative contract for every public behavior change. Update both RPC contract files only when a shared model, command, or event surface is affected. Update architecture, Architecture Decision Record, standards, and this index when a boundary, phase, or migration status changes.
- Keep headings concrete and maintainable. Avoid marketing language and unrelated comparisons.
- Do not introduce names, branding, identifiers, copied text, or copied code from other projects. References may inform expected behavior only; implementation and documentation must be original.
- Do not mention unrelated products anywhere in this documentation set.
