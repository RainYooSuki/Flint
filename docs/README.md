# Flint Documentation

This directory is the maintained documentation set for Flint. It separates current contracts and operational guidance from the accepted target architecture that is still being migrated.

## Status note

The application currently ships as a **partially modularized monolith**:

- Rust now uses a Cargo workspace rooted at `src-tauri`. The host package remains `flint`; `flint-core`, `flint-feature-api`, and `flint-provider-api` are extracted foundation crates. `flint-core` also owns shared path/network/error policy and object-safe typed port contracts; the remaining feature/provider implementation crates are not extracted yet.
- All four Cargo workspace packages share the generated date-based release version: the host `[package] version` matches `[workspace.package] version`, and non-root members use `version.workspace = true`. Release tooling keeps the host and workspace versions identical and updates every local `Cargo.lock` package entry as part of the same five release paths (`VERSION`, `package.json`, `src-tauri/tauri.conf.json`, `src-tauri/Cargo.toml`, `src-tauri/Cargo.lock`).
- Phase 1 ModProvider **registry/selection milestone** is implemented in `src-tauri/crates/flint-provider-api/src/lib.rs` and `src-tauri/src/mods/providers.rs`, with shared mod operations selecting through the provider registry. Shared typed port contracts now exist in `flint-core`, but provider adoption/context decomposition and full checker enforcement remain Phase 4/5 work.
- Phase 2 LoaderProvider **registry/leaf milestone** is implemented in `src-tauri/src/loaders/providers.rs`: six independent loader leaves, list/install contexts, progress sink, deterministic selection, and the preserved 75-second/600-second timeout split. The full phase remains partial because full `LoaderProviderContext` port decomposition and checker enforcement are deferred to Phase 4/5.
- Phase 3 contribution registry is implemented in `src/core/contributions.ts`, `src/app/composition.ts`, `src/app/App.tsx`, `src/app/AppSidebar.tsx`, `src/modules/settings/index.tsx`, and `src/modules/launch/index.tsx`. Pages, navigation, five settings sections, and a launch-navigation instance action are populated and mounted. `AppPageContext` exposes the frozen slot lists; `src/core/ContributionBoundary.tsx` and `src/core/InstanceActionRenderer.tsx` provide the shared renderers.
- `scripts/check-architecture.mjs`, its tests, and the release workflow architecture gate are implemented. The `flint-release.yml` `prepare` job installs frontend dependencies, runs the checker tests, then runs `node scripts/check-architecture.mjs --phase 3`; all build-matrix jobs depend on `prepare`. The active gate enforces frontend manifest/composition/import boundaries, module/provider import and selection boundaries, forbidden std/process/fs patterns, exact allowlists, exact workspace members, and the host 30-command/28-feature-command gating map while intentionally allowing reqwest/shared-client and reviewed parent-helper waivers. The runtime contribution registry owns duplicate-ID, page-target, and ordering validation; the static gate does not re-run those checks. It does not enforce provider adoption of the shared typed ports; Phase 4 Cargo metadata and provider-port consumption gates remain pending.
- Phase 4 is **in progress**: the workspace root plus `flint-core`/`flint-feature-api`/`flint-provider-api` foundation, shared core policy/typed-port contracts, and host lifecycle/availability milestone are implemented. `flint-feature-api` provides the feature descriptor, validated registry, lifecycle coordinator/state machine, and availability DTO; `src-tauri/src/feature_host.rs` composes seven explicit features and real provider metadata, starts in Tauri setup, publishes the ungated `get_host_availability` snapshot, gates all 28 feature commands, filters frontend contributions, and shuts down on exit. Full provider adoption/decomposition of typed contexts and runtime lifecycle, the full 19-crate extraction, remaining feature-module extraction, and Phase 5 hardening remain pending.
- Existing command names, arguments, success results, DTOs, and events are preserved. Phase 4 adds the ungated `get_host_availability` command and gating/error behavior for the 28 existing feature commands, documented in `API_CONTRACT.md`.

The full provider adoption/decomposition of typed contexts and runtime lifecycle, remaining feature/provider crate extraction, and remaining feature-module extraction remain planned; the workspace, feature lifecycle API, host lifecycle/availability IPC/gating, and snapshot-driven frontend filtering remain implemented. See the canonical phase-status table in [`ARCHITECTURE.md`](ARCHITECTURE.md#canonical-migration-phase-status), and [`DEVELOPMENT_STANDARDS.md`](DEVELOPMENT_STANDARDS.md) for the phase applicability matrix and concise current-phase cross-reference.

Canonical ownership: [`ARCHITECTURE.md`](ARCHITECTURE.md) is the detailed source for boundaries, provider/registry semantics, lifecycle, frontend contributions, and phases; [`DEVELOPMENT_STANDARDS.md`](DEVELOPMENT_STANDARDS.md) owns process/checklists/concise summaries; the [Architecture Decision Record](architecture-decision-records/0001-modular-core-and-feature-modules.md) documents rationale/consequences; this README is the index/source-of-truth map.

## Documentation rules

- Label behavior as **Implemented**, **Partially implemented**, **Planned**, or **Deferred**, and identify the migration phase/milestone. Never present full provider adoption/decomposition of typed ports/runtime lifecycle, not-yet-extracted feature/provider implementation crates, full host feature-module extraction, or later-phase checker gates as implemented/active before they are; the host lifecycle/availability IPC/gating/filtering milestone is implemented and may be stated as such.
- Use only relative Markdown links that resolve inside `docs/`. Do not link to another checkout, an external site, or a repository file outside the documentation tree.
- Update the affected authoritative contract for every public behavior change. Update both RPC contract files only when a shared model, command, or event surface is affected. Update architecture, Architecture Decision Record, standards, and this index when a boundary, phase, or migration status changes.
- Keep headings concrete and maintainable. Avoid marketing language and unrelated comparisons.
- Do not introduce names, branding, identifiers, copied text, or copied code from other projects. References may inform expected behavior only; implementation and documentation must be original.
- Do not mention unrelated products anywhere in this documentation set.
